## 1. 关闭窗口时，如何保持响应并等到线程真正回收？

**触发条件。** 检测、保存或 helper 还在运行时关闭窗口；尤其 `QThread::finished / isFinished()` 已出现，但 DeferredDelete 或线程局部对象析构仍未结束。过早销毁资源会越过原生线程清理边界；在 GUI 中等待又会阻塞事件处理。

**设计与实现。** [MainWindow::closeEvent](../../src/ui/mainwindow.cpp)将首次关闭转为异步协议；[OperationCoordinator](../../src/app/operationcoordinator.cpp)协调各资源所有者，保留事件循环并拒绝新操作；[MainWindow::initializeOperationCoordinator](../../src/ui/mainwindow_lifecycle.cpp)注册各参与者及应用级 thread-retirement 屏障。启动前由 [AsyncThreadRetirement::watch、Ticket::check](../../src/app/asyncthreadretirement.h)接管 QThread：`finished` 触发后台 `wait()`，原生 join 完成后才在 GUI 循环中清除所有者记录、删除线程并释放应用屏障。Ticket 自持有；所有者提前消失时跳过回调，仍完成回收。[DetectionController::requestShutdown / isShutdownReady](../../src/app/detectioncontroller.cpp)展示领域接入方式。

**取舍。** 关闭时间由实际收尾决定，不强制终止 C++ 线程；增加 ticket、后台回收和轮询状态，换取 GUI 不同步等待及资源生命周期可观察。已接受的写入仍需完成，因此“点击关闭立即返回”不等于“程序立刻退出”。Qt 的完成语义来自 [QThread 文档](https://doc.qt.io/qt-6.8/qthread.html#isFinished)，不是项目另创线程机制。

**如何验证。** [window_shutdown_tests.cpp::orphanNativeThreadTailRemainsInApplicationCloseBarrier](../../tests/window_shutdown_tests.cpp)用可阻塞的线程尾部清理制造该窗口，断言 GUI heartbeat 继续推进、孤立 ticket 仍阻止关闭；同文件 `runningRealOnnxTaskClosesWithoutBlockingGui` 和 `highResolutionAcceptedAutomaticSaveDrainsBeforeDestruction`覆盖真实 ONNX 任务和已接受保存。夹具见 [thread_retirement_fixtures.h](../../tests/thread_retirement_fixtures.h)。

历史从 [PR #64：界面与异步关闭集成](https://github.com/misaka-ning/vision-studio/pull/64)到 [PR #66：等待原生线程回收](https://github.com/misaka-ning/vision-studio/pull/66)；后者修补 `finished` 不足以证明 native cleanup 完成的边界。[原生回收验收索引](native-thread-retirement-acceptance.json)及其链接保留当时的 red/green 证据，不能当成本次重跑结果。

## 2. 推理快于保存或切换配置时，如何交付结果？

**触发条件。** 连续图片推理产生高分辨率结果，后台落盘尚未完成；用户停止、换参数或重跑子范围，旧写入又迟到。无界排队会放大内存，直接写盘会阻塞界面，旧完成回调可能污染新缓存。

**设计与实现。** [WorkbenchConfiguration::compose / configurationFingerprint](../../src/app/workbenchconfiguration.cpp)与 [OperationCoordinator](../../src/app/operationcoordinator.cpp)在任务准备阶段冻结配置、顺序、文件身份和保存选项；[DetectionController::prepareTask / acceptImageResult / acknowledgeImageResult](../../src/app/detectioncontroller.cpp)管理任务快照及 ticket。Worker 等当前结果确认后再继续，见 [InferenceWorker](../../src/core/inferenceworker.cpp)中的结果交付与 ack 路径。

[ResultDeliveryService::acceptImage / complete](../../src/app/resultdeliveryservice.cpp)将缓存、历史快照和串行 [ResultWriter](../../src/app/resultwriter.cpp)串起；成功、失败、过期完成都释放同一 ticket。[ImageResultStore](../../src/app/imageresultstore.cpp)以配置指纹、源文件身份及 generation 约束缓存提交。临时 PNG 成功写入后才释放内存像素，失败保留内存结果；写入请求共享持有临时目录。旧 generation 的完成不能覆盖新缓存，相同配置的子范围重跑保留范围外有效结果。

**取舍。** 图片吞吐受结果交付/存储速度约束，以限制在途结果和保护交互响应；落盘失败保留像素会增加内存占用，不能宣称绝对内存上限。任务快照使当前运行不随界面编辑漂移，需要明确失效规则和过期完成处理。异步保存不是丢弃错误：当前写入失败会通知用户。

**如何验证。** [result_delivery_tests.cpp](../../tests/result_delivery_tests.cpp)中的 `staleCompletionAcknowledgesWithoutFailingNewConfiguration`、`shutdownIsAsynchronousIdempotentAndDrainsAcceptedResults`、`sameConfigurationRerunPreservesResultsOutsideNewRange`分别验证过期 ack、异步排空与子范围保留；[inference_delivery_tests.cpp](../../tests/inference_delivery_tests.cpp)核查 Worker 背压；[workbench_configuration_tests.cpp](../../tests/workbench_configuration_tests.cpp)核查配置权威与快照。历史设计及拆分见 [PR #62](https://github.com/misaka-ning/vision-studio/pull/62)、[PR #63](https://github.com/misaka-ning/vision-studio/pull/63)和 [stage4b 验收](stage4b-acceptance.json)。

## 能力边界与检查

模型架构与训练来源属于各模型；ONNX 推理由 OpenCV DNN / ONNX Runtime 执行，PT/TorchScript 由常驻 Python/PyTorch 后端执行，Netron 提供模型图可视化。项目自身可审查的工程实现是调度、状态权威、配置快照、结果交付、保存与 Qt 页面集成，不把第三方算法调用称为原创算法。[依赖与构建指南](../开发指南.md)、[模型说明](../模型说明.md)、[完整架构](应用架构.md)给出进一步边界。
