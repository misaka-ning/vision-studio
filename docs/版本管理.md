# 版本管理与发布

本仓库的源码主线为 `main`，正式版标签使用 `vX.Y.Z`，编号预发布使用 `vX.Y.Z-beta.N`。GitHub [Releases](https://github.com/misaka-ning/vision-studio/releases) 保存逐版安装包、完整对应源码、校验清单和更新说明；验收材料保存到仓库的 `docs/releases/evidence/<完整应用版本>`，本地工作目录保存当前开发状态。

## 版本号与历史

应用版本采用 `主版本.次版本.修订版本`：不兼容的公开行为／数据格式变化提升主版本，兼容的新功能提升次版本，兼容的修复提升修订版本。Debian 包修订号独立记录，例如应用 `1.5.0` 对应包 `1.5.0-1`；仅包修订变化时明确记录原因，不改写既有文件。

预发布采用编号 beta，例如应用 `2.0.0-beta.1`、标签 `v2.0.0-beta.1`、DEB `vision-studio_2.0.0-beta.1-1_amd64.deb`；发行目录、说明、证据和源码归档均使用完整应用版本 `2.0.0-beta.1`。Debian 的 `~` 保证 beta 排在同版正式包之前，编号按数字排序。[Debian 版本规则](https://www.debian.org/doc/debian-policy/ch-controlfields.html#version)、[语义化版本规范](https://semver.org/)。目前工具接受正式版本和 `-beta.N`，尚不接受其他预发布名称或构建元数据。

DEB 内部 Control 的 Version 是 `2.0.0~beta.1-1`，文件名则使用安全的 `-beta.1`。APT／DPKG 按内部版本排序，与文件名无关。发布附件只使用 ASCII 字母、数字、`.`、`_`、`-`，避免 GitHub 重写特殊字符后使远端文件名与校验清单不一致。[GitHub 资产文件名说明](https://docs.github.com/en/rest/releases/assets#upload-a-release-asset)。

CMake 使用 `project(VisionStudio VERSION 2.0.0 LANGUAGES CXX)`，并以 `set(VISION_STUDIO_APP_VERSION "2.0.0-beta.1")` 给出完整应用版本。两者的数字部分必须一致；旧正式标签只有 `project VERSION` 时仍可核验。打包与源码工具从这些字段派生默认版本，避免多处硬编码。GitHub Actions 的 `v*` 标签检查同时校验完整版本和同版 Release 说明。

已公开的标签和三个核心发行文件保持不可变。不移动标签、不用另一份内容覆盖同名 DEB 或完整源码包。需要修正应用或核心发行内容时，创建新的版本或明确的新 Debian 包修订，并发布新的校验值。维护说明可以在 `main` 修正，历史归档仍保留交付时内容。

维护者已要求将每个历史 Release 整理为三个手动附件：先把旧 QA、日志和说明保存到同版仓库证据目录，再移除额外附件。此整理只改变页面附件列表和说明链接，保留 DEB、完整源码包及原 `SHA256SUMS` 的内容，不重新生成冻结归档。

GitHub 已启用主线保护，禁止强制推送或删除 `main`，并要求线性历史。版本标签 `v*` 的远端规则禁止更新和删除；后续创建新标签不受影响。PR 使用 squash 合并，合并后的功能分支自动清理。源码与发布工具检查由只读 GitHub Actions 执行，完整 Qt／模型／安装验收仍在目标环境完成。

1.1.0–1.5.0 是从既有本地发行包整理到仓库的历史版本。版本依据原包中的 CMake 版本与冻结源码，功能依据发行说明和 QA 日志；补录日期与本地验收日期在 [更新日志](../CHANGELOG.md) 中说明，GitHub 的公开发布时间以 Release 页面为准。不要伪造历史开发提交或把补写文档混入原归档。

## 每次更新流程

1. 在功能分支开发，检查真实行为并提交必要测试；更新 `CHANGELOG.md` 的「未发布」条目。
2. 确认发行版本，统一 CMake、界面、打包默认值及发行文档中的版本号，将对应日志移入带版本号的条目，并创建 `docs/releases/X.Y.Z.md` 作为本次独立 Release 说明。
3. 合并到 `main`，在目标环境完成 Release 构建与 CTest，准备发行 runtime，运行真实 ONNX／PT、模型显示、录制等相关验收。记录实际执行结果，保存到 `docs/releases/evidence/X.Y.Z`。
4. 使用 `packaging/build_deb.py` 生成 DEB，使用源码交付工具生成完整对应源码包；运行 `verify_deb.py`、隔离安装验收及源码校验。构建与依赖交付步骤见 [打包说明](../packaging/README.md) 和 [对应源码与重建](release/对应源码与重建.md)。
5. 确认 Git 工作树中所有发行源码、更新说明与验收证据已提交，记录构建提交和 SHA256。创建带说明的 `vX.Y.Z` 标签并推送 `main` 与标签。
6. 以同名标签创建 GitHub Release，附更新说明和仓库证据链接，只上传 DEB、完整对应源码包与 `SHA256SUMS` 三个附件。较大的上游源码与应用拆分归档已在完整源码包内，不重复提交到 Git 或零散上传 Release。
7. 从远端核对标签与提交，确认 Release 已公开且资产完整，通过远端内容 SHA256／下载复核确认资产与本地一致，保留发布凭证。完成后才允许清理旧版本目录。

用户已授权以后每次版本更新同步到 GitHub，因此以上步骤和下述发布工具是本项目每次更新的必需流程。完成本地构建不算发布完成；应继续推送源码、标签和 Release，并完成远端校验。此流程在每次实际版本更新时执行，无需额外建立定时任务。

如果上传或校验失败，保留本地文件，修复并继续发布。不要因为仓库中已存在同名文件就认定上传成功，也不要在远端备份完成前释放空间。

## 项目发布工具

`scripts/github_release.py` 使用已登录的 GitHub CLI。以下以新版本 `1.6.0` 为例，需先完成上述构建、QA、独立 Release 说明和源码提交；不得仅改示例命令就发布未验收版本。

```bash
# 在发行提交上建立带说明的标签，源码和标签必须先推送
git tag -a v1.6.0 -m "Vision Studio 1.6.0"
git push origin main
git push origin v1.6.0

# 先检查本地和远端状态，不创建 Release
python3 scripts/github_release.py publish --version 1.6.0 \
  --release-dir output/releases/1.6.0 \
  --notes-file docs/releases/1.6.0.md --dry-run

# 发布该版本，并核验上传资产
python3 scripts/github_release.py publish --version 1.6.0 \
  --release-dir output/releases/1.6.0 \
  --notes-file docs/releases/1.6.0.md

# 可独立重做远端校验
python3 scripts/github_release.py verify --version 1.6.0 \
  --release-dir output/releases/1.6.0
```

工具默认使用仓库 `misaka-ning/vision-studio`，默认项目目录为脚本所在仓库根目录。发布要求工作树干净、当前 `HEAD` 等于该版本标签，并核对已推送的远端标签与本地提交一致。正常发布不覆盖已公开的三个核心文件；中断的草稿只有显式指定 `--resume-draft`，且检查为同版本、同文件内容后才可续传。

编号 beta 使用相同的 `publish`／`verify` 命令，将 `--version`、目录和说明路径改为完整的 `2.0.0-beta.1`。发布工具根据后缀明确设置 `prerelease=true` 与 `latest=false`，不替换当前正式版 Latest；beta 草稿只能按同类预发布续传，类型不符会拒绝，不会修改既有 Release。[GitHub 预发布规则](https://docs.github.com/en/rest/releases/releases#create-a-release)。预发布继续要求全部适用 QA、最终 DEB SHA256、源码清单与三个资产的远端校验，不能使用 beta 身份跳过验收。

```bash
python3 scripts/github_release.py publish --version 2.0.0-beta.1 \
  --release-dir output/releases/2.0.0-beta.1 \
  --notes-file docs/releases/2.0.0-beta.1.md --dry-run
```

整理 1.1.0–1.5.0 等历史包时，若原版没有后续才引入的 QA 报告，可以在 `verify` 添加 `--legacy`。它仍校验关键归档、原始清单和远端资产，不用于跳过新版本的完整验收要求。

## NVIDIA GPU 版本的交付检查

V1.6 起正式 DEB 继续携带完整离线 CPU／Netron 环境，同时交付 `gpu_setup.py`、`gpu_probe.py`、`setup_gpu.sh` 和 GPU 版本／SHA256 锁。GPU 库由用户明确操作后一次配置到用户目录，不把多 GB CUDA wheel 塞入 DEB，不增加 Release 附件，不在 DPKG maintainer scripts 联网或更改驱动。

每次更新必须核验 GPU 依赖锁、许可通知、目录保护、取消与原子发布；并在受支持的 NVIDIA 硬件上实测 PyTorch 和 C++ ONNX Runtime 的 GPU 推理，覆盖实际设备、CPU／自动回退、错误报告、灰度 C1／C3、左右目、检测／分类、取消及录像。GPU 下载完成不代表模型／UI／正式包验收完成。V1.6 起发布工具要求 `gpu-qa.json`（schema_version=1）绑定最终 DEB SHA256；必须有实际 CUDA 节点、PT CUDA、安装包 ONNX／PT CUDA、CPU 回归、灰度 C1／C3、左右目与录像全部通过的真实记录。报告的 `success` 与各 check 不得提前填写为 true。隔离离线安装仍验证 CPU 可以独立使用，未配置的 GPU 探针不下载或写入安装树。

```bash
/usr/bin/python3.10 -m unittest discover -s tests -p gpu_runtime_tests.py -v
./scripts/setup_gpu.sh
/usr/bin/python3.10 scripts/gpu_probe.py
```

GPU 环境的 `ready.json`、`installed-packages.txt`、`gpu-license-inventory.json` 与 `GPU-THIRD-PARTY-NOTICES.md` 记录实际版本与原始许可。CUDA／cuDNN 组件保留 NVIDIA 许可，不能声明为应用的 AGPL 源码；应用完整源码包包含配置脚本、依赖锁和说明。GPU 用户环境及共享 pip 缓存属于用户资料，发行目录清理不得删除。

每个 GitHub 手动资产必须小于 2 GiB；按实际文件大小校验，不能只凭估算。每版仍为以下三个手动附件，加 GitHub 自动提供的两个源码入口。[GitHub Release 限制](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)。

## Release 文件与验收证据

每版只有以下 **3 个手动上传的附件**：

| 文件 | 用途 |
| --- | --- |
| `vision-studio_X.Y.Z-N_amd64.deb` | Ubuntu 22.04 amd64 安装包，默认目录 `/opt/VisionStudio` |
| `vision-studio-X.Y.Z-complete-source.tar.xz` | 配套应用源码与需要交付的第三方对应源码、来源和通知 |
| `SHA256SUMS` | DEB 与完整源码包两个主文件的 SHA256 |

页面另外有 GitHub 自动提供的 **Source code (zip)** 与 **Source code (tar.gz)** 两个入口，由平台生成，不能从 Release 中移除。它们来自 Git 标签，不包含大体积上游对应源码，不能替代 `complete-source.tar.xz`。

完整源码包内部已包含 `vision-studio-X.Y.Z-sources.tar.xz` 应用拆分归档、`SOURCE-SHA256SUMS`、`SOURCE-INVENTORY.json`，以及对应上游源码、来源、许可和原始通知，需要时从完整包解压取得。公开转发安装包时，继续提供对应源码、通知与校验文件。

QA 报告、日志、原始说明与必要预览保存到 `docs/releases/evidence/X.Y.Z`，随仓库提交并在同版 Release 说明中链接，不另外上传为零散附件。附件减少不降低验收要求：后续每次发布仍须完成适用的测试、真实推理、安装与源码校验，保留实际结果；历史证据迁移保留原文件，不重写原报告。

## 本地只保留最新两版

以已完成远端核验的正式发行版本号排序，本地只保留最新两个版本的发行源码副本、安装包与独立构建目录。预览版本和未成功上传版本不自动纳入清理，当前工作树和唯一未备份资料不能删除。

2.0.0 正式发布并完成远端核验后，最高两个正式版本为 2.0.0 与 1.6.0，应保留这两版的发行与独立构建副本。已公开 Beta 的本地副本不由默认 `prune` 删除，须逐版验证标签、三个远端资产及 SHA256，再按精确路径单独清理；其历史 Git 标签、Release、证据和用户数据继续保留。

预发布期间必须保留当前正式版作为可用回退版本。默认 `prune` 仍保护最高两个正式版本，并完全保留 beta 目录；因此发布一个 beta 不会自动触发正式版删除。若维护者要求最终只保留「最新 beta + 当前正式版」，需对其他旧发行／构建副本逐版核对标签、远端三个资产及 SHA256，再按精确路径单独清理，不新增宽泛匹配或放松工具门禁。

清理工具应先列出计划及可释放空间，再依据发布凭证执行；只处理明确识别的旧版目录和旧版文件。不得清除 Git 元数据、当前工作树、共享 Qt SDK／runtime、用户自备模型、设置、运行记录、导出结果或录像。历史源码仍可通过远端标签检出，完整依赖与安装包通过该版本 Release 下载。

```bash
# 默认只列计划，不删除
python3 scripts/github_release.py prune --releases-root output/releases

# 原始清单及远端文件大小、SHA256 全部核验通过后才删除旧整版目录
python3 scripts/github_release.py prune --releases-root output/releases --execute

# 主文件夹中的独立发行副本同样先查看计划，再执行
python3 scripts/github_release.py prune \
  --releases-root "$HOME/VisionStudio/releases"
python3 scripts/github_release.py prune \
  --releases-root "$HOME/VisionStudio/releases" --execute
```

`prune` 保护最高两个正式版本号，只识别标准的整版发行目录。预览与执行都会先核验最高两个本地版本是否已完整正式发布；存在草稿、缺失或不完整上传时，整次退出并保留全部版本，完成发布后重试。早期 1.1.0 直接放在发行根目录中的文件，以及 `build/`、`output/deb-stage/` 等构建或暂存副本不由它猜测删除；首次历史整理需要先记录明确清单并核验远端，再单独处理。之后新版本应统一使用 `output/releases/X.Y.Z` 布局。

本地保留策略只减少可重新获取的发行／构建副本，不使用 Git 历史重写来节省空间。已发布历史仍保留在仓库及 Release，后续每次成功发布后重复执行同一策略。
