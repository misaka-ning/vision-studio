# 对应源码与重建

本次交付的两个主文件为 DEB 与 `vision-studio-2.1.0-complete-source.tar.xz`，由 `SHA256SUMS` 校验。完整源码包包含应用源码归档 `vision-studio-2.1.0-sources.tar.xz`、`sources/` 下的原始上游源码、`SOURCE-INVENTORY.json` 及校验内部文件的 `SOURCE-SHA256SUMS`。新编写的代码按 AGPL-3.0-only 发布，维护者为 misaka_ning <1468549029@qq.com>。源码清单记录各份上游源码的来源、版本和哈希；模型的独立来源及哈希记录在 `models/` 的 provenance 文件中。

## 构建应用

在 Ubuntu 22.04 amd64 上准备 C++17 编译器、CMake ≥ 3.21、Qt 6.8.3 Core / Gui / Widgets / Svg / Network / WebChannel / WebEngineWidgets / Test 开发文件，以及系统 OpenCV 4.5.4 开发文件。Qt WebEngine 的间接依赖包括 Qml / Quick / QuickWidgets / Positioning；SDK 还须带 `libexec/QtWebEngineProcess`、`resources/` 与 `translations/qtwebengine_locales/`。Qt SDK 可以放在其他目录；通过 `CMAKE_PREFIX_PATH` 指定。

```bash
tar -xf vision-studio-2.1.0-sources.tar.xz
cd vision-studio-2.1.0
cmake -S . -B build/release -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=ON \
  -DVISION_RESOURCE_FALLBACK=/opt/VisionStudio \
  -DCMAKE_PREFIX_PATH="$HOME/Qt/6.8.3/gcc_64"
cmake --build build/release -j
```

重新准备发行用独立环境时，使用 Ubuntu 的 Python 3.10。`requirements-release.lock.txt` 是根据发行环境实际元数据生成的 59 项版本清单，包含 Netron 9.3.1、ONNX 1.17.0 和 protobuf 6.33.0；安装时禁止额外依赖解析，以保留发行用无 GUI OpenCV wheel。

```bash
python3.10 -m venv build/release-runtime
build/release-runtime/bin/python -m pip install --upgrade pip
build/release-runtime/bin/python -m pip install --no-deps \
  --extra-index-url https://download.pytorch.org/whl/cpu \
  -r docs/release/requirements-release.lock.txt
VISION_STUDIO_PYTHON="$PWD/build/release-runtime/bin/python" \
  ctest --test-dir build/release --output-on-failure
```

依赖初次准备需要网络；依赖准备后，本地推理、模型显示与转换可离线执行。`scripts/setup_pt.sh` 是便携版环境准备脚本；正式发行重建应使用 `docs/release/requirements-release.lock.txt`，以保留本次实际捆绑的无 GUI OpenCV 与 Netron 版本。

Netron 官方 PyPI 此版本只提供 wheel，因此源码包另带官方 v9.3.1 tag 的完整 Python / JS 源码。若需要从该源码重建安装包，在解压后的 Netron 根目录执行：

```bash
python3.10 package.py build version
/应用环境绝对路径/bin/python -m pip install --no-deps ./dist/pypi
```

上游命令复制前端文件并按 tag 元数据写入 9.3.1 版本信息。运行时不需要 Electron 或 Node 开发依赖；Node 在下文重建 QtWebEngine 时属于构建工具。

## 模型转换依赖与原始源码

2.1.0 新增 `scripts/model_convert.py` 和 Qt 转换页。转换在 CPU Python 后台进程执行，使用 PyTorch 2.9.1、ONNX 1.17.0 和 Python protobuf 6.33.0；ONNX 导出显式 `dynamo=False`，固定 FP32、batch=1、C1／C3、不含 NMS，TorchScript 保存 `config.txt`。无需安装 ONNX Script、ONNX Slim 或独立 ONNX Runtime 导出依赖。输出加入库后可应用任务、类别、输入尺寸和通道，手工标签优先。UI 管理名称、备注、路径和结果，模型转换不修改来源文件。

完整源码包从原 15 份增加至 18 份上游源码／构建输入；新三份身份如下，完整来源与校验记录在 `SOURCE-INVENTORY.json`：

| 文件 | 字节数 | SHA256 |
| --- | --- | --- |
| `onnx-1.17.0.tar.gz` | 12,165,120 | `48ca1a91ff73c1d5e3ea2eef20ae5d0e709bb8a2355ed798ffc2169753013fd3` |
| `protobuf-33.0.tar.gz` | 6,872,665 | `cbc536064706b628dcfe507bef386ef3e2214d563657612296f1781aa155ee07` |
| `protobuf-cpp-3.21.12.tar.gz` | 4,842,303 | `4eab9b524aa5913c6fffb20b2a8abf5ef7f95a80bc0701f3a6dbb4c607f73460` |

Python 分发版本 `protobuf==6.33.0` 对应上游 v33.0 源码；ONNX 官方 Linux wheel 的构建配方另将 C++ protobuf 3.21.12 静态链接入原生扩展。这不是在 Python 环境并存两个 protobuf 发行版，不应将 Python 6.33.0 降成 3.21.12。完整 v33.0 包保留 Python／UPB 原生实现及构建文件，C++ 3.21.12 包用于 ONNX 原生扩展重建。ONNX 源发行包含其 pybind11；四份原始 LICENSE 与归档成员哈希在 `packaging/licenses/model-conversion/PROVENANCE.json`，发行安装后位于 `/usr/share/doc/vision-studio/licenses/model-conversion/`。

需要从源码重建 ONNX 原生扩展时，先以对应 3.21.12 包构建静态 protobuf，启用 PIC、禁用其测试并安装到专用前缀，再通过 `PATH`、`CMAKE_PREFIX_PATH` 指向同一前缀构建 ONNX 1.17.0。依据随包 ONNX 的 `workflow_scripts/protobuf/build_protobuf_unix.sh` 与 manylinux 配方；未指定已有 protobuf 时，ONNX CMake 可能改为下载 22.3 与 Abseil，不能把这一默认回退当作当前 wheel 的构建身份。官方 [ONNX 源码构建](https://github.com/onnx/onnx/tree/v1.17.0)、[Linux protobuf 配方](https://github.com/onnx/onnx/blob/v1.17.0/workflow_scripts/protobuf/build_protobuf_unix.sh)与原始配置已随源码保存。

Python protobuf 原生 wheel 可按 v33.0 的 `python/README.md`，在完整源码根目录执行 `bazel build //python/dist:binary_wheel`；仅需 Python 源包时使用 `//python/dist:source_wheel`。前者针对所选系统 Python 构建，Bazel 和其上游声明的构建工具／依赖应按原配置准备。不要直接对完整 GitHub 源码目录执行 `setup.py`；上游只对生成的 Python 源包支持该方式。[protobuf v33.0 构建说明](https://github.com/protocolbuffers/protobuf/blob/v33.0/python/README.md)。

发行重建使用上述 59 项 headless 锁；开发 `requirements-pt*.txt` 保留开发用 OpenCV 配置，只增加 ONNX／protobuf，不可将其 GUI OpenCV 环境冒充正式 DEB 运行时。

## 可选 GPU 环境与源码范围

正式 DEB 继续包含完整离线 CPU／Netron 环境；GPU CUDA wheel 不嵌入 DEB 或完整源码包。应用源码包含 `gpu_setup.py`、`gpu_probe.py`、`setup_gpu.sh`、完整 `requirements-gpu*.txt` 版本／官方 SHA256 锁和 C++ ONNX Runtime API 接口。GPU 环境使用 PyTorch `2.9.1+cu128`、Torchvision `0.24.1+cu128`、ONNX Runtime 1.23.2；运行库从官方源下载至用户目录。

```bash
./scripts/setup_gpu.sh
/usr/bin/python3.10 scripts/gpu_probe.py
```

系统 Python 3.10 需要 venv 模块（Ubuntu `python3.10-venv`）；GPU 初次准备需要网络、已有 NVIDIA 驱动及至少 20 GB 空间。`--runtime-dir` 指定专用用户目录；成功自检后原子发布 ready.json，取消／失败保留旧环境。不修改 CPU runtime 或 GPU 驱动。下载库只保留 wheel 原字节，不做 strip 或 DEB 的 GNU 库替换。

GPU 环境内保存实际发行版／许可清单和原始 wheel 通知。NVIDIA 专有组件保留自身许可，不能把它们当作本应用 AGPL 对应源码；本项目发行包不再分发这些可选 GPU 库。其他随包组件继续依下文提供完整对应源码与重建材料。

## 重建 Qt 与允许替换

可从八份 Qt 原始归档重建共享库。先构建 qtbase，再使用其安装前缀的 `bin/qt-configure-module` 配置 qtsvg、qtwayland、qtimageformats、qtdeclarative、qtwebchannel、qtpositioning，最后配置 qtwebengine。QtWebChannel 与 QtWebEngine 要求此前的 Qml / Quick 依赖已安装。操作系统开发依赖与启用特性应覆盖 XCB、Wayland、SVG、图像插件和 WebEngine。上游配置、CMake 文件和嵌入源码均保留在归档中。有关配置参数见 [Qt 构建说明](https://doc.qt.io/qt-6.8/build-sources.html)。下列 Qt 命令在包含 `sources/` 的发行目录或完整源码包解压根目录执行；若当前在 `vision-studio-2.1.0` 应用源码目录，先返回上一级。

```bash
tar -xf sources/qtbase-everywhere-src-6.8.3.tar.xz
mkdir qtbase-build
cd qtbase-build
../qtbase-everywhere-src-6.8.3/configure -prefix "$HOME/qt-6.8.3-modified" \
  -release -opensource -confirm-license -nomake examples -nomake tests
cmake --build . -j
cmake --install .
```

每个额外模块解压后，在独立构建目录执行 `"$HOME/qt-6.8.3-modified/bin/qt-configure-module" /模块源码绝对路径`，然后执行 `cmake --build . -j` 与 `cmake --install .`。

QtWebEngine / Chromium 的构建比应用本身需要更多工具，包括支持 C++20 的编译器、Node、Python 与 html5lib、Ninja、gperf、bison、flex，以及 Linux 的 pkg-config、NSS 和图形开发依赖。版本要求以配套 6.8.3 源码配置检查为准；[Qt WebEngine 平台说明](https://doc.qt.io/qt-6.8/qtwebengine-platform-notes.html)列出各平台要求。官方 6.8 文档会随 LTS 补丁更新，不能用网页当前版本号替代本次 6.8.3 归档的身份。

发行程序通过共享库动态链接 Qt；允许用户修改 Qt、替换 Qt 库及插件，或重新构建应用并链接修改后的 Qt。发行版没有禁止为调试库修改而进行的逆向工程，也不要求签名才能执行修改版本。兼容的替换前缀应包含 `lib/libQt6Core.so.6`、`plugins/platforms/`、`libexec/QtWebEngineProcess`、WebEngine 的 `resources/` 及 `translations/qtwebengine_locales/`。

```bash
VISION_STUDIO_QT_HOME="$HOME/qt-6.8.3-modified" vision-studio
```

启动器将该前缀的 `lib` 放在 `LD_LIBRARY_PATH` 前面，并使用其 Qt 插件、WebEngine 辅助进程、资源与语言目录。应用使用 RUNPATH，使这一覆盖能够生效。Qt ABI、启用特性和依赖须与应用要求兼容；若有不兼容修改，可使用完整应用源码重新构建。

## 发行运行时的实际变更

Python wheel 的 `.py` 文件、许可证和第三方 NOTICE 保留。为使用 Ubuntu 的系统 GNU 运行库，`packaging/build_deb.py` 在**暂存副本**中核验需要的 ABI / 符号版本，再将 NumPy 等本机扩展的 GNU 库依赖改为系统 `libgfortran.so.5`、`libquadmath.so.0` 和 `libgomp.so.1`，删除 wheel 内的对应副本，并据实际 ELF 依赖生成 Debian Depends。

OpenCV wheel 的旧 LP64 OpenBLAS 依赖 gfortran3，不能直接改为 gfortran5。本次将其 BLAS / LAPACK 入口改为 Ubuntu `libblas.so.3` 与 `liblapack.so.3`，核验入口符号后删除其旧 OpenBLAS。NumPy 所用独立 ILP64 OpenBLAS 保留。脚本是这些变更的完整记录；不会修改原始虚拟环境或系统 Qt SDK。系统 GNU 运行库通过系统软件包提供，其对应源码由 Ubuntu 软件包仓库提供。

FFmpeg 来自 OpenCV 无 GUI wheel，实际 `av_version_info()` 返回 **5.1.6**，实际库报告 LGPL 2.1 或以后版本。它的源码、原始 wheel 构建 Dockerfile 与实际 `avutil_configuration()` 均随本次交付保存。FFmpeg 源码和 wheel 中的 FFmpeg 库均未修改。Python wheel 保留原 RUNPATH；上述 BLAS / GNU 变更只重绑定指定库的 DT_NEEDED。应用与 Qt 的 RUNPATH 调整由打包脚本记录。[FFmpeg 许可及源码说明](https://ffmpeg.org/legal.html)

## 生成并检查 DEB

完整参数和系统打包依赖见 `packaging/README.md`。使用源码中的 `packaging/build_deb.py`，指定已构建应用、Qt SDK、额外 QtImageFormats 插件目录和发行用 runtime。脚本创建全新暂存目录，推导系统依赖并生成 `vision-studio_2.1.0-1_amd64.deb`。`packaging/verify_deb.py` 在普通用户环境解包检查版权、源码校验、运行库、模型、桌面入口、路径及真实推理；`packaging/verify_install_namespace.py` 在隔离命名空间内执行安装、普通用户运行及卸载检查。

2.1.0 本轮新增模型库名称／备注／移除管理、后台 PT → ONNX／TorchScript 转换及输出入库元数据应用。Qt／Netron、推理与可选 GPU 约定保持，原 15 份上游材料字节不变，新增三份转换依赖源码，使总数为 18；独立 CPU runtime 为 59 项。Qt SDK、源码通知与 QtImageFormats SPDX 沿用已保存原记录，没有把 Python 清单重收当作重建 Qt。应用源码、清单与完整源码包按本版重新生成，不能以 2.0.0 二进制或应用源码包替代。新发行目录为 `output/releases/2.1.0/`，可复用已核验不可变的原始上游归档，旧 DEB、归档与清单不覆盖。

打包和源码归档使用由 Git／明确授权输入构成的干净源目录；目录递归本身不按 Git 跟踪状态过滤，不能把其他任务文件、个人训练资料或输出复制进公开归档。新 helper 必须进入 DEB 的明确文件复制列表；存在于源码的 `scripts/` 不代表已部署。

冻结代码前可先执行清单检查；此命令只核验上游文件并写入当前版本的清单与发行依赖锁，不生成源码归档：

```bash
python3 docs/release/build_source_archive.py --source-root /干净源码绝对路径 \
  --release-directory output/releases/2.1.0 --inventory-only
```

本版构建与功能验收完成后，先生成正式 DEB，再运行下文的源码归档命令。最后在发行目录执行 `sha256sum -c SHA256SUMS` 和 `sha256sum -c SOURCE-SHA256SUMS`，并用 `verify_deb.py --source-dir` 核对配套来源。源码打包时会嵌入原始上游归档，公开清单只包含 DEB 和完整源码包；内部清单覆盖应用源码与各份上游材料。

本版仅重收实际 Python 发行版通知，保留未变化的 Qt 快照；在应用源码根目录可执行：

```bash
python3 - <<'PYTHON'
from pathlib import Path
from docs.release.collect_licenses import python_licenses
python_licenses(Path('build/release-runtime'), Path('packaging/licenses'), {'pip'},
                '/opt/VisionStudio/runtime',
                Path('output/releases/2.1.0/sources/netron-9.3.1-source.tar.gz'))
PYTHON
```

需要改变或重建 Qt 时再使用 `collect_licenses.py` 的完整 CLI，传入匹配的 SDK、八份源归档及 QtImageFormats 前缀重新收集；上游原通知保持字节。转换依赖的四份源码 LICENSE 按 `model-conversion/PROVENANCE.json` 指定成员从匹配归档保留。Python 清单完成后执行 `build_source_archive.py --inventory-only`，据实际元数据生成发行锁，随后冻结源码与包内材料。

构建与真实验收完成、最终 DEB 已生成后，再从干净源码根目录生成归档：

```bash
python3 docs/release/build_source_archive.py --source-root /干净源码绝对路径 \
  --release-directory output/releases/2.1.0
```

最终源码集合／字节检查另有独立报告随标签保存，未通过不发布；报告在归档后加入仓库以避免递归自校验。所有功能、CPU／CUDA 与安装验收只记录真实执行结果，不沿用旧版通过数字。

这些步骤用于重建功能与打包内容，不承诺在不同编译器、容器或操作系统开发环境下产生逐字节相同的二进制。每份已交付文件的身份以该次发行 `SHA256SUMS` 为准。许可完整条款以随包原文为准；本说明记录了交付与重建方法。
